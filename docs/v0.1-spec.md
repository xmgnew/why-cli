# why v0.1 specification — Linux process + CPU

状态：v0.1 目标设计，部分已实现。设计基线日期：2026-09-14。当前实现与验证结果见 [implementation guide](implementation.md)。

本文规定目标行为，不代表当前 CLI 已支持全部功能。现有命令见 [usage guide](usage.md)。所有检测阈值是 v0.1 工程默认值，不是统计显著性或已验证的准确率承诺。

## 1. 产品契约

回答：**在已记录的时间内，整机 CPU 是否明显上升，哪些被观测到的进程贡献了这次上升？**

- Linux、普通用户、procfs 轮询、确定性算法；不依赖 root、eBPF、LLM。
- 首版针对宿主机视角。不解释 cgroup 配额、容器 CPU 上限、单核瓶颈、调度延迟或“机器卡顿”的真实原因。
- 记录启动之前的历史不可恢复。CPU 百分比为采样区间平均值，“峰值”必须标为“采样峰值”。
- 进程短于采样间隔时可能完全漏掉；采到一次也可能无法获得有效 CPU 差值。未知贡献必须保留，不能猜给父进程。
- 输出分为 observed（测量）、correlated（时间关联）、likely contributor（增量贡献推断）。不输出因果证明、退出码或精确退出时间。

首版闭环：`why watch` 前台记录并持有内存历史；另一终端 `why` / `why 60s` / `why cpu` 查询该 recorder，默认最近 60 秒。用用户私有运行目录内的 Unix socket，仅同 UID 可查询；不建永久 daemon、不持久化原始数据。watch 停止后历史消失，无 recorder 时明确提示先启动。当前实现使用私有运行目录、同 UID 校验和有界文本协议；具体命令与限制见 [usage](usage.md)。安装方式仍可后续完善，不影响本文算法。

## 2. 核心默认值

| 参数 | v0.1 决定 |
|---|---|
| 采样周期 | 1 秒，固定节拍，按实际时间计算 |
| 有效采样区间 | 0.5–1.5 秒；超过范围保留原始数据但不用于检测 |
| 最大正常扫描耗时 | 200 ms；超出标记 attribution 时序质量不足 |
| 历史 | 目标 300 秒；记录数据预算 64 MiB，先到者先淘汰 |
| 基线 | 最近连续 30 个有效非事件区间，至少 10 个才能检测 |
| 确认尖峰 | 连续 2 个区间满足进入条件 |
| 确认恢复 | 连续 3 个区间满足退出条件 |
| 元数据刷新 | 首次发现；之后每 10 秒；comm 改变时提前刷新 |
| 元数据单项上限 | cmdline 4 KiB，cwd/exe 各 4 KiB，显式记录截断 |

当前原型将 64 MiB 分为 48 MiB 历史与 16 MiB 归因分析预留（含临时数组）。

64 MiB 是受控记录数据预算，不承诺整个进程 RSS 恰好低于 64 MiB。活动表、索引、字符串、事件摘要也必须有界；活动身份上限 32768，达到上限时采用确定性轮转采集并标记扫描不完整，禁止据此推断消失。不能用“只保存 top N”作为常态，因为会破坏增量归因。

## 3. 数据模型：事实、区间、解释分开

逻辑 schema 先固定，不冻结 C struct 的内存布局或跨平台 ABI。计数器用无符号 64 位整数，时间用纳秒，差分先检查单调性；缺失值不是 0。

| 实体 | 必需字段与含义 |
|---|---|
| RecordingSession | session_id、boot_id、procfs/PID namespace 范围描述、CLK_TCK、配置/算法版本、时钟锚点、权限/扫描状态 |
| ProcessIdentity | session 内 `(pid, starttime_ticks)`；跨 session 引用同时携带 session_id 和 boot_id |
| ProcessObservation | identity、read_begin/end、utime/stime、ppid、state、comm、num_threads、读取状态 |
| ProcessMetadata | identity、observed_at、cmdline/cwd/exe 可选值及各自状态；版本化保存，不能回写旧历史 |
| ParentObservation | child identity、parent identity 可空、原始 ppid、observed_at、解析依据；表示当时观测关系 |
| SystemObservation | read_begin/end、user/nice/system/idle/iowait/irq/softirq/steal/guest/guest_nice 原始计数器、在线 CPU 集合 |
| ScanFrame | sequence、scan_begin/end、system observation、process observations、枚举是否完成、各类错误/跳过计数 |
| CpuInterval | 起止时间、原始差值、CPU seconds、系统 busy%、有效性与误差标记、端点 observation 引用 |
| LifecycleObservation | FIRST_SEEN、NO_LONGER_OBSERVED、VISIBILITY_LOST、METADATA_CHANGED；时间边界与证据 |
| CpuIncident | id、start/end 区间、detected_at、peak interval、冻结基线/阈值、状态、贡献结果、数据质量、算法版本 |

CPU 与生命周期不能统一伪装成一个精确时间点事件：CPU 是区间量；首次见到是观测事实；退出通常只知道观测消失。

### 身份与父子关系

- PID 重用后 starttime 改变，必须是新身份，绝不跨身份相减。
- starttime 的 tick 精度仍有极罕见碰撞边界；v0.1 不声称这是内核永不碰撞的全局 ID。
- 父进程需解析到身份，不能长期保存裸 PPID 后查询“现在这个 PID 是谁”。同帧父身份需满足父启动不晚于子启动；无法确定则 parent unknown。关系仍标为 polling observation。
- 父子关系是历史边，reparent 后追加观测，不覆盖旧关系。已经退出但仍被历史引用的父元数据保留。
- exec 不改变进程身份；comm/cmdline/exe 变化只是元数据变化证据。两次采样之间的 exec 可漏掉，不能称为完整 exec history。
- 同名进程不能自动当成同一应用；PGID、session ID 也不能自动当作一项任务。

### 读取生命周期

FIRST_SEEN 不等于此刻启动；另存 starttime 的内核启动时间信息。首次样本之前的 CPU 默认不补入当前窗口。

完整扫描中未再枚举到身份，或确认对应 proc 项消失，可记录 NO_LONGER_OBSERVED；边界是最后成功观测到首次确认缺失之间。它不保证精确终止时刻。读权限失败、解析失败或不完整扫描记录 VISIBILITY_LOST/unknown，不能解释成退出。Z 状态单独记录为观测到 zombie。

## 4. 采样与 CPU 口径

### 4.1 数据来源

`/proc/stat` 取系统计数器；`/proc/<pid>/stat` 取字段 1/2/3/4/14/15/20/22；cmdline、cwd、exe 仅作可选上下文。CLK_TCK 从 sysconf 获取，不硬编码 100。utime 已含 guest time，cutime/cstime 属于已等待的子进程时间，不能加进当前进程 CPU。[Linux proc_pid_stat 手册](https://man7.org/linux/man-pages/man5/proc_pid_stat.5.html)

只枚举 `/proc` 顶层进程，读取进程级 CPU，不再遍历 task 把线程 CPU 加一遍。stat 的 comm 可含空格及右括号，不能直接按空格拆整个文件：识别 PID 与括号包围的 comm，按最后一个闭括号后的数值字段解析并严格验证。

### 4.2 一轮扫描

1. 记录 scan_begin；读取系统计数器，记录读取前后时间。
2. 枚举进程，逐项记录 stat 读取时间。新增身份读取元数据，随后复核 stat 身份；身份改变则丢弃混合元数据。尽量通过同一 proc 目录 FD 读取；仍不声称跨文件原子快照。
3. 已有身份按刷新规则读取上下文；轮转扫描起点，避免始终忽略尾部 PID。
4. 记录 scan_end、完整性和错误。计数器时间点取各次读取中点，保留读取跨度。
5. 下一次按绝对节拍唤醒，不采用“做完再睡一秒”。迟到时跳过错过的节拍，不补造样本。

procfs 存在进程退出/复用竞争，打开的旧 proc FD 不会变成新进程的 FD；这有助于身份隔离，但不提供全系统一致快照。[Linux procfs 文档](https://www.kernel.org/doc/html/latest/filesystems/proc.html)

### 4.3 时钟与断档

区间计算用 CLOCK_MONOTONIC；同时保留 BOOTTIME/REALTIME 锚点。MONOTONIC 不随墙钟跳变且不含休眠；BOOTTIME 包含休眠。[Linux clock_gettime 手册](https://man7.org/linux/man-pages/man2/clock_gettime.2.html)

BOOTTIME 与 MONOTONIC 增量差超过 100 ms 视为休眠断点。采样迟到、CPU 在线集合变化、计数器异常均产生质量事件；受影响系统区间不参加检测。活动事件以 interrupted 结束，不宣称恢复；重新积累至少 10 个有效区间。墙钟改变只影响显示映射。

### 4.4 系统 CPU

令 Δ 表示相邻有效读取之差：

```
ΔT = Δuser + Δnice + Δsystem + Δidle + Δiowait + Δirq + Δsoftirq + Δsteal
ΔB = Δuser + Δnice + Δsystem + Δirq + Δsoftirq
busy_pct = 100 × ΔB / ΔT
busy_seconds = ΔB / CLK_TCK
```

guest/guest_nice 不重复加入总量。iowait、steal 单列，均不算本机执行 CPU；irq/softirq 算 busy，但不保证能归给进程。iowait 可能回退；v0.1 保留原值并使该区间无效，不静默钳成 0。ΔT≤0 或参与计算的计数器回退同样无效。[Linux proc_stat 手册](https://man7.org/linux/man-pages/man5/proc_stat.5.html)

这是整机 0–100% 的定义，可能与其他工具的“非 idle”口径不同。CPU busy 高不等于发生调度饱和。steal 很高但 busy 低时，不归咎本机进程。

### 4.5 进程 CPU

```
cpu_seconds(p) = (Δutime + Δstime) / CLK_TCK
cores_used(p)  = cpu_seconds(p) / 实际进程读取间隔秒数
core_pct(p)    = 100 × cores_used(p)
```

100% 表示一个逻辑 CPU，800% 表示八个逻辑 CPU。系统整机百分比与进程 core_pct 必须标注不同分母。主展示优先 CPU seconds 与平均 cores_used。

只对相邻轮次、相同身份且有效的观测差分；新发现或中间读取失败后先建立新端点，不跨缺口把累计量塞进某一秒。消失后的尾部 CPU 不外推，cutime/cstime 也不用于“补齐孩子”。

### 4.6 时间对齐

系统区间为标准分析窗口。每个有效进程区间按与系统区间的重叠时长分配 CPU seconds，假设区间内均匀消耗；标明这是分箱估计，不是 tick 的精确执行时间。保留未对齐边界，缺失不补 0。归因等待下一轮提供右边界数据，允许比检测多延迟约 1 秒；最新事件显示 provisional。

对于跨进程区间的分配必须守恒：所有分箱 CPU seconds 之和不得超过原始差值。查询与事件边界同样采用比例裁切；不足完整区间的峰值保留原区间说明，不捏造更细粒度峰值。

## 5. Spike detection：固定规则与状态机

检测对象仅为整机 busy_pct。单线程吃满 64 核中的一核通常不会触发本规则；仍能在窗口 CPU 排名中看到它。

### 基线与进入条件

从候选出现之前的最近最多 30 个连续有效非事件区间取：

```
b = median(busy_pct)
mad = median(abs(busy_pct - b))
rise = max(20 percentage points, 3 × 1.4826 × mad)
enter = max(50%, b + rise)
exit  = b + max(10 percentage points, rise / 2)
```

进入条件为 busy_pct ≥ enter。不把 enter 截成 100%；若其超过 100%，当前基线下没有可检测的这类尖峰。持续高 CPU、缓慢爬升可能不触发突发检测，查询仍报告峰值/均值/进程排名，不声称“没有异常”。

### 状态转移

| 状态 | 处理 |
|---|---|
| WARMUP | 至少 10 个连续有效区间后进入 IDLE；此前只提供 CPU 概况 |
| IDLE | 先用既有基线判断新样本；满足进入条件则冻结基线、阈值和该基线窗口，进入 CANDIDATE；否则更新基线 |
| CANDIDATE | 下一有效区间仍 ≥ enter 则 ACTIVE；start 回溯为首个候选区间左边界，detected_at 为确认时刻 |
| 候选失败 | 回到 IDLE，将两个区间按顺序加入基线；单区间突发只保留在概况中 |
| ACTIVE | 持续更新峰值；低于或等于 exit 开始恢复计数；高于 exit 清空恢复计数 |
| 恢复确认 | 连续 3 个区间 ≤ exit 时关闭；end 是首个恢复区间左边界，三段恢复数据不计入事件 |
| 关闭后 | 清空旧基线，以 3 个恢复区间开始重新 warmup；不立刻重复触发 |
| 任意状态断档 | 清空候选/基线；活动事件标 interrupted；重新 warmup |

ACTIVE 时不更新基线，避免把持续高占用吸收成正常。未确认恢复时事件仍 ongoing，query 边界不是事件终点。恢复候选区间暂存，恢复失败才纳入事件汇总。长事件保留累计量与有界摘要，原始前段淘汰后标 history_truncated；不无限固定原始样本。

例：基线 14%、MAD=2 个百分点，enter=50%、exit=24%。80%、87% 确认尖峰；随后 20%、18%、16% 确认恢复。87% 是某一秒的平均峰值，不是瞬时峰值。

## 6. Attribution：先测量贡献，再解释增量

不用“启动得早 + 名字像编译器”打一个黑箱分数。不输出未经校准的 confidence=0.91。

### 6.1 两种排名必须分开

对事件区间 W 的每个进程 p，使用第 4.6 节对齐值 c(p,i)：

```
A(p) = Σ c(p,i)                       # 事件内已记录 CPU seconds
r(p) = 基线窗口内 CPU seconds / 有效覆盖秒数
X(p) = Σ max(0, c(p,i) - r(p) × 覆盖秒数(p,i))
```

A 是总活动排名；X 是相对自身常态的正增量排名。新进程若 starttime 明确在基线结束之后，可设 r=0；其首样本之前仍不补 CPU。已存在进程需覆盖至少 80% 基线时长才能计算 r，否则 r/X unknown，只参加 A 排名。按 CPU 率的加权均值计算 r，避免采样长度偏差。

默认“谁贡献了这次上升”按 X 降序；unknown 单列；A 降序提供完整活动视图。并列按 A、identity 排序，保证回放确定性。

为什么需要两份排名：常驻服务一直吃 4 核，另一个进程从 0 增到 3 核；前者总量最大，后者才是此次上升的主要已知贡献者。

X 是正向增量，下降的进程不会抵消其他进程的 X；因此 ΣX 不等于系统净增量，不能声称 X/系统净增量 是因果占比。

### 6.2 汇总与未归因量

```
S = Σ 系统 busy_seconds
P = Σ A(p)
accounted_ratio = P / S              # S > 0 才定义
residual_seconds = S - P             # 保留有符号值
```

accounted_ratio 仅是 CPU 核算覆盖指标，不是“看到了多少进程”的比例或概率。残差可能含漏采短命进程、退出尾部、不可见进程、中断处理和计数/扫描误差，不能全部标成“未知进程”。P>S 时不把进程值归一化到 100%，报告核算不一致。

busy_seconds、P、irq/softirq 的数值只作为并列信息，不从残差机械扣除中断值来构造严格守恒账本。collector 自身 CPU 包含在排名及分母中，标记为 why recorder，不偷偷排除。

### 6.3 分组：保守且不重复计数

v0.1 的排名原子单位是进程身份。展示层仅合并“在本次事件中观测到同一直接父身份，且 exe 路径相同”的兄弟进程。exe 不可读时用同一父身份 + comm 作弱分组，显式标注名称分组；父未知不合并。关系/程序标签在事件内变化的进程保持单列。

- 组 A/X 为成员求和；任一成员 X unknown，组 X 标 partial，不能获得主要增量贡献者标签。
- `clang × 8` 中 8 是本窗口不同身份总数，不自动表示同时运行 8 个。
- `make → clang × 8` 中 make 是父上下文；clang 的 CPU 不算到 make 自身。make 若自身用 CPU，独立计量。
- 不把 shell、PID 1 或所有祖先递归汇总进主排名；v0.1 不自动识别“整项构建任务”。祖先链最多展示 8 层，避免环并标记截断。
- 每个身份只能出现于一行贡献总量；树展开是细节，不得再次加到合计。

多层 `make → sh → compiler` 可展示已有链条，但不保证折叠成一个 build。这是明确的首版能力边界，而不是用不可靠启发式填补。

### 6.4 likely contributor 判定

先定义分析质量门槛：事件已完成且未截断；基线与事件无系统断档；扫描均完整且 ≤200 ms；进程有效差值覆盖至少 90% 的“可见进程 × 可观测时间”（从首次成功读取到最后成功读取，不包括其前后未知生命周期）；0.8 ≤ accounted_ratio ≤ 1.05；具有可计算 r 的进程覆盖至少 80% 的 P。任何门槛失败仍显示测量排名与缺失原因，但不输出主要增量贡献者标签。

在质量通过时，令 E=Σ 所有 r 已知进程的 X。只有 E>0 才评估组/进程 g：

- X(g)/E ≥ 50%；
- X(g)/S ≥ 10%；
- 有效 CPU 差值至少来自 2 个进程采样区间；
- g 无部分基线、混合身份或未知 X。

满足则显示“主要的已观测 CPU 增量贡献者”。门槛是产品规则，不是因果置信度。没有唯一主要贡献者时列 top 3 与其余汇总，不强行选一个。ongoing 事件可显示 provisional 排名，暂不下最终标签。

生命周期时间关联只作文字证据：启动估计及其 tick/采样误差确实位于 start 前后 2 秒内，才写“启动时间接近 CPU 上升”；消失区间与恢复前后 2 秒重叠，只写“不再被观测到的时间与恢复接近”。区间不能确定先后时不得打印“提前 0.7 秒”。关联本身不增加 CPU 贡献。

## 7. 历史、查询与输出

按完整旧 frame 淘汰历史；进程身份/元数据按引用保留，但也受总预算约束，必要时更早淘汰 frame。摘要数上限 1024，每项只保留 top 20、others、unknown 和质量信息；摘要淘汰同步更新实际可查询范围。分析器内部状态也计入预算；无法保留基线时重新 warmup，不能无界占用。

query 返回实际覆盖范围；没有足够基线、记录中断、历史已淘汰、没有达到尖峰阈值分别说明。查询某事件的子窗口时，明确区分“完整事件结果”与“本次查询片段数值”，不混用分母。

默认输出依次是：

1. 观测时间范围、采样分辨率、整机平均/采样峰值。
2. CPU 上升事件的基线、开始/恢复时间区间或 ongoing。
3. 增量贡献排名：CPU seconds、平均使用核数、相对基线新增 CPU seconds。
4. 可选父链与带观测时间的 cwd/command。
5. 核算覆盖、未归因残差及具体限制；只有满足规则时才有 likely contributor。

未发生 spike 也返回“未检测到符合规则的整机 CPU 尖峰”和窗口内总 CPU 活动排名。CPU 很高但从记录开始就如此时，说明缺少更早基线。

cmdline 可能含敏感参数，默认只显示程序名，展开 command 由用户主动请求；内存记录本地且有界，不读取 environ。控制字符必须转义；元数据不可用不妨碍 CPU 计量。不存在的 cwd 不回填为当前 cwd。

## 8. 实现前即可确定的验收案例

以下是 v0.1 的测试契约；其中部分已由当前测试覆盖，实际验证范围以实现文档为准。

| 输入场景 | 必须得到的行为 |
|---|---|
| 8 核、1 秒，ΔT=800 ticks、ΔB=640，HZ=100 | 系统 80%；某进程 200 ticks = 2 CPU seconds = 200% 单核口径 |
| guest 非零 | 系统与进程 guest 不重复计数 |
| iowait 回退、ΔT=0、计数回退 | 区间无效，不制造尖峰或负 CPU |
| PID 相同、starttime 不同 | 两个身份，不相减、不继承父链 |
| comm 含空格/右括号；cmdline 为空/截断 | 解析正确，字段缺失有明确状态 |
| 多线程进程 + 被 wait 的子进程 | 线程不重复加；子进程不经 cutime 再加一次 |
| 全部发生在两次采样间的短命任务 | 系统峰值可能可见，归因未知；不编造进程 |
| 首次见到已有高累计 CPU 的进程 | 不把整个生命期 CPU 放到当前秒 |
| 读权限失败或扫描预算耗尽 | unknown/partial；不批量记录退出 |
| 14% 稳态 → 80%、87% → 20%、18%、16% | 一个事件；确认延迟 1 个区间；结束回溯首个恢复区间 |
| 14% → 90% → 14% | 不确认事件，但概况保留 90% 采样峰值 |
| 持续 90%、单核占满多核机器 | 不强造上升；总活动排名仍可查 |
| A 常驻 4 核，B 从 0 到 3 核 | A 总量排名更高，B 增量排名更高 |
| 两个不同父身份的 clang | 不按名字跨任务合并 |
| 父退出/重挂靠/PID 重用 | 保留旧关系；不把旧孩子挂到新同 PID 父亲 |
| 基线缺失或 P/S=0.3、1.2 | 显示排名与质量问题；不打印主要增量贡献者标签 |
| 时间对齐与裁切 | 分配总 CPU 不超过原区间；不补齐缺失尾部 |
| 休眠、墙钟跳变、CPU 热插拔 | 休眠/热插拔断档；墙钟变化不改变 CPU 率 |
| 事件超过历史长度、内存/身份上限 | 内存有界、明确截断/不完整，不伪造完整解释 |

原型阶段另做 Linux 实机验证：空闲、持续 CPU 任务、并行编译、进程风暴；测 recorder CPU、RSS、扫描 p50/p95/p99、实际保留长度和残差。暂定普通负载目标：1000 可见进程、1 Hz 时 recorder 平均少于一个逻辑 CPU 的 1%，扫描 p95<100 ms。目标未达就调整采集成本与默认值，不能提前写入 README 当成绩。

## 9. 设计基线与后续工作

冻结：计数口径、身份/时钟语义、缺失不为零、原始观测与派生区间分层、1 Hz 默认、MAD 基线状态机、总量/增量双排名、保守分组、质量门槛、有限历史。

实现阶段可以通过 fixture 与实测调整数值阈值，但必须更新算法版本和验收案例。当前原型采用 C17 与 CMake，已完成采集、元数据、历史缓冲、时间区间对齐、尖峰检测和总量/增量归因排名（含保守同父分组与质量门槛）。已实现前台记录器与跨终端查询接口（1–300 秒窗口，完整事件与窗口总量分开展示）。下一步补齐祖先展开及自动生命周期关联解释，并进行性能基准测试；稳定二进制格式、通用插件接口和 macOS 抽象仍不属于当前工作范围。


### 当前查询实现边界

`why watch` 持续记录，`why` / `why Ns` / `why cpu [Ns]` 默认查询最近 60 秒。
查询终点为最新系统观测，不外推到当前时间；展示观测年龄及缺失前缀。
窗口总量单独计算；重叠事件按完整事件展示，不将原事件增量当成子窗口增量。
单次最多展示最近 8 个重叠事件，并报告省略数；这不是持久化摘要格式。
当前仍在单线程中同步生成有界报告，复杂查询可能延迟采样，断档必须继续暴露。
通信仅使用本地私有 Unix socket，退出清理 socket、释放历史，保留空锁文件用于安全重启。
